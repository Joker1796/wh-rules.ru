## Этап 1 — типы. Подробно

### Почему так, а не «переписать на TypeScript»

- **JSDoc + `// @ts-check` в `.js`** даёт ту же проверку, что `.ts`, но код и сборка остаются
  прежними: Vite не читает типы, комментарии вырезаются при минификации. Значит, сборка
  **байт-в-байт** та же — это и есть гарантия «ничего не сломать», и её можно проверить.
- Переименовать в `.ts` можно позже, по файлу, когда типы уже описаны. Vite умеет `.ts` сам.
- Начинаем с `rosterEngine.js`: чистые функции без Vue, 197 тестов, самый сложный и самый
  переиспользуемый модуль (его импортируют ~60 файлов) — максимум пользы на единицу риска.
- Компоненты `.vue` (это `vue-tsc`) — не на этом этапе: сначала их разрезать (этап 2).

### Решения, которые нужны от владельца

- **Версия TypeScript.** Последняя — 7.0 (новый компилятор на Go). В памяти записано: переход
  5→7 высокий риск (для api). Предлагаю **5.x, как в `wh11ed-api` (`^5.7.2`)**: проверка JSDoc в
  5.x зрелая, у обоих репозиториев одна версия. На 7 — отдельно, вместе с api.
- **Строгость.** Сначала `strict: false`, только явные ошибки; `noImplicitAny` и прочее — по
  файлу, позже.

### Шаги

**Шаг 0. Снять точку отсчёта** (до любых правок, на чистой ветке от `main`):
- `npm run build` → сохранить список файлов `dist/` с хешами (sha256). После каждого шага сборка
  должна дать **те же хеши**. Если нет — найти, почему, до движения дальше.
- Зафиксировать: тестов 2727, линтер чистый.

**Шаг 1. Подключить проверку, ничего не проверяя:**
- `typescript` (5.x, точная версия) в `devDependencies` — в бандл не попадает.
- `tsconfig.json`: `allowJs`, `checkJs: false`, `noEmit`, `moduleResolution: "bundler"`,
  `resolveJsonModule`, `types: ["vite/client"]` (для `import.meta.glob` в `data/roster/index.js`),
  `include` — только `src/composables/roster*.js` и `src/data/roster/**`.
- Скрипт `npm run typecheck` = `tsc -p tsconfig.json`. Должен пройти с нулём ошибок (файлы ещё
  не помечены `@ts-check`).
- Проверить: хеши сборки те же, тесты и линтер зелёные, `eslint` не начал читать `tsconfig`.

**Шаг 2. Описать данные ростера одним файлом типов:**
- `src/composables/roster.types.js` — только `@typedef`, без кода: определение юнита из
  сгенерированных `src/data/roster/<slug>.js` (`id`, `sid`, `name`, `kws`, `flags`, `sizes[{pts,
  per, default}]`, `step`, `defaults`, `gear[{m, t, in, o}]`, …), запись юнита в ростере (`uid`,
  `unitId`, размер, снаряжение, улучшение, warlord, заметка), детачмент, сам ростер
  (`{ faction, detachments, battleSize, customPoints, checkLegality, units }`).
- **Ключи не угадывать:** собрать скриптом полный набор ключей по всем 30 файлам данных и по
  местам, где записи создаются (`addUnitEntry`, миграции в `useRosters`) — тип должен покрыть
  каждый.
- **Гейт против расхождения:** тест, который проходит по всем 30 файлам и падает на ключе, не
  описанном в типе. Генератор (`gen-roster-data.mjs`) добавил поле — тест красный, пока тип не
  дописан. Иначе типы тихо устареют (урок «гейты должны кусаться»). Доказать красным на
  подставленном ключе.

**Шаг 3. `// @ts-check` в `rosterEngine.js`:**
- JSDoc на 95 экспортов: параметры и результат через типы из шага 2.
- Каждую ошибку `tsc` разобрать в одну из двух куч:
  - **нужна аннотация** (`?.` на заведомо существующем поле, неочевидный тип) — правка
    комментария, без изменения кода;
  - **настоящий баг** (обращение к несуществующему полю, `undefined` в арифметике очков) — НЕ
    чинить в том же коммите: сначала падающий тест, потом правка, отдельным коммитом, с записью
    в журнал.
- Правило коммитов: коммит с аннотациями не меняет ни одной исполняемой строки — проверяется
  хешами сборки (они должны совпасть).

**Шаг 4. Проверка в CI:**
- Шаг `npm run typecheck` в `.github/workflows/ci.yml` рядом с линтером. Иначе проверка
  останется «руками» и сгниёт.

**Шаг 5. Проверка перед слиянием:**
- Хеши `dist/` совпадают с шагом 0 (кроме намеренных багфиксов из шага 3 — их перечислить).
- `npm test` (2727+), `npm run lint`, `npm run typecheck`, `npm run build`.
- Если были багфиксы — стенд: открыть тестовые ростеры (`npm run test-rosters`), правка
  снаряжения, очки, лидеры; владелец смотрит.

**Шаг 6. Дальше по файлу** (каждый — свой коммит, тот же порядок 3→5): `rosterEnhEligible`,
`rosterValidation`, `rosterModifiers`, `rosterStatMods`, `rosterImport`, `rosterExport`, затем
`useTracker` и сетевые `useAuth`/`useCloudSync`/`useParty`. Затем — `noImplicitAny` по файлам.

### Что может сломаться и как ловим

| Риск | Ловушка |
|---|---|
| Изменился бандл | сравнение хешей `dist/` на каждом шаге |
| Тип разошёлся с генератором | тест-гейт на ключи (шаг 2) |
| «Починили» поведение под типы | правило: код меняется только с падающим тестом, отдельным коммитом |
| ESLint/IDE начали ругаться иначе | прогон линтера на каждом шаге; конфиг линтера не трогаем |
| Проверка заброшена | шаг в CI |
| Нагрузка на машину владельца | `tsc` по ~20 файлам — секунды; полный vitest — анонсировать, `--maxWorkers=2` |
