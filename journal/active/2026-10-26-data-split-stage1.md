## Постановка (владелец, 2026-10-26)

Первый этап — только разделить логику и данные. В бандле живёт актуальная версия данных. Игрок может
«скачать» более старую версию: тогда **весь сайт** показывает ту версию данных, сверху неубираемый
баннер «устаревшая копия». Этап завершается целиком, прежде чем браться за следующие. Механизм сверки
(`npm run sync`), гейты и генераторы ломать нельзя.

## Что есть сейчас (замер 2026-10-26)

- `src/data` — 22 МБ, 93 записи верхнего уровня. Вперемешку **данные правил** (датащиты, фракции,
  ростер, модификаторы, MFM, тексты Core Rules и Event Companion, Combat Patrol, FAQ, сгенерированные
  индексы) и **содержимое приложения** (чейнджлог, справка, туториал, настройки трекера, лендинг,
  опции печати, цвета диспозиций) и даже **код** (`deepOverlay.js`, `slugify.js`, `extractSubheadings.js`,
  `data.types.js`).
- Код приложения импортирует данные из **132 файлов статически** и из 29 — лениво. Чаще всего
  `factionsIndex.js` (36), `roster/*` (27), `trackerOptions.js` (22), `eventCompanion.js` (14).
  Тяжёлое уже ленивое: загрузчики `loadDatasheets`, `loadRosterFaction`, `loadRosterModifiers*`,
  фракции, Combat Patrol, индексы поиска.
- **87 из 100 скриптов** (sync, генераторы, гейты) читают `src/data` по пути.
- Версия данных — одно число `APP_DATA_VERSION` (`src/data/appDataVersion.js`) + `mfmVersion`. В git
  были 912 → 913 → 931 → 963 → 981 → 995. Тегов релизов в git нет.
- Готовые защиты: без SW во вкладке (2.9.5), `npm run dsids` + `markReconcile` (сборка со старыми
  данными «сливает, но не чистит» отметки), чанки старых сборок живут месяц.

## Ключевое решение: как старая версия попадает на сайт

**Вариант А (рекомендую): та же сборка, другие данные — копия сайта на подпути.**
- При выкате собирается ещё одна копия приложения **из того же кода**, но с архивными данными правил:
  `wh-rules.ru/archive/981/`. Подмена — на уровне сборки (алиас пути данных), код не знает, какая
  версия у него внутри, кроме флага «архив».
- Тот же origin → те же localStorage и аккаунт; код текущий → схема ростеров та же, порчи нет
  (в отличие от «старой сборки на поддомене» из журнала 18.10).
- Багфиксы логики сразу работают и на старых данных.
- Рефакторинг 132 файлов не нужен; 87 скриптов не трогаем — актуальные данные остаются в `src/data`.

**Вариант Б: переключение версии внутри одного приложения во время работы.**
- Все данные идут через асинхронный слой, архивная версия скачивается модулями с CDN.
- Это перевод 132 файлов со статических импортов на асинхронные + ожидание данных на каждом экране.
- Нужен позже для кастомных бандлов (этап 5), но для «весь сайт на старой версии» избыточен.

Общая проблема обоих: **старые данные + новый код**. Форма данных меняется (`joins` у ростера 25.10,
новые условия модификаторов). Значит у архива должна быть «версия схемы» и проверка совместимости при
каждом выкате; несовместимое — мигрировать или снимать версию с архива. Чем меньше версий храним, тем
дешевле.

## План этапа (под вариант А)

### 1.1 Граница: что такое «данные правил»
- Разметить каждый файл `src/data` в один из трёх видов: **правила** (зависят от версии GW),
  **приложение** (всегда текущее), **код** (переехать в `src/composables` / `src/utils`).
- Разрезать смешанные файлы. Кандидаты: `factionsIndex.js` (список фракций — данные; цвета,
  готовность, группы — приложение), `armyTrackers` (логика трекеров + тексты), `rosterModifiers/conditions.js`
  (словарь условий — его читает логика, а записи ссылаются на него).
- Решить судьбу сгенерированного: индексы поиска, `sourceIds.json`, `datasheetIds.json`,
  `datasheetRenames.json`, `patches/` (страница патчей — приложение, всегда текущая).
- **Гейт:** манифест `src/data/manifest` (или поле в каждом файле) — новый файл в `src/data` без
  разметки валит тест. Гейт «код не лежит в `src/data`».
- Пути не меняем: все 87 скриптов и все гейты работают как раньше.

### 1.2 Подменяемый корень данных в сборке
- Алиас `@rules` (или аналог) → `src/data` по умолчанию; переменная окружения сборки указывает на
  архивный снимок. Код приложения импортирует данные правил только через алиас; данные приложения —
  как раньше.
- **Гейт (eslint `no-restricted-imports`):** данные правил — только через алиас; линтер, как и
  сейчас, в CI.
- Проверка: обычная сборка до/после побайтно совпадает по составу чанков (`check-chunk-graph.mjs`),
  `npm run perf` и `smoke` без регресса — игрок ничего не замечает.

### 1.3 Снимок версии (архив)
- Снимок версии N = файлы-«правила» из **последнего релиза на версии N** (со всеми нашими правками
  RU и модификаторов), плюс `manifest.json`: версия данных, версия MFM, версия приложения, дата,
  версия схемы.
- Хранится в отдельном репозитории (рабочее имя `wh-rules-data-archive`), клонируется рядом, как
  appdata: в wh11ed не тащим по 20 МБ на версию (история wh11ed чистилась в 2026-09).
- Скрипт `npm run archive:freeze` — снимок из указанного коммита; шаг в скиле `appdata-update`:
  перед бампом данных заморозить уходящую версию.
- Тегировать релизы в git (`v2.10.6`) — чтобы «последний релиз на версии N» был адресуем.

### 1.4 Сборка и выкат архива
- `deploy.sh` после основной сборки собирает каждую хранимую версию: тот же код, корень данных →
  снимок, `base` = `/archive/<N>/`, флаг архива.
- Архив: без SEO-страниц, `noindex`, не в `sitemap`, `Disallow: /archive/` в robots.
- Хранить **1–2 прошлые версии** (решение владельца). Старше — удаляется с сайта.
- Время выката растёт на одну сборку на каждую хранимую версию.

### 1.5 Режим архива в интерфейсе
- **Неубираемый баннер** сверху на каждой странице: «Архивная копия: правила версии 981 (MFM 1.5,
  до 16.10.2026). Актуальная версия — перейти». Без крестика.
- Вход: пункт в ⚙ «Версия правил» и ссылка со страницы патчей («смотреть сайт по прошлой версии»).
- Футер, печать ростера, экспорт списка пишут версию данных (печать и экспорт уже пишут —
  проверить, что берут архивную).
- Ростер, сохранённый в архиве, помечается версией данных; в актуальной версии у него плашка
  «собран по 981». Валидация и очки — по версии, где открыт.
- Отметки (избранное, коллекция): архив не чистит — проверить `markReconcile` на архивной сборке.
- Совместная партия: лобби сверяет версию данных у обоих телефонов; разные — не стартует.
- Облако: синхронизация работает как обычно (код и схема те же) — подтвердить на стенде.

### 1.6 Офлайн
- Вкладка: архив — обычные страницы, грузятся по запросу.
- Установленное приложение: SW корня покрывает `/archive/…`. Precache архив **не** включает
  (вес установки прежний). Кнопка «Скачать для офлайна» в режиме архива прогревает его файлы в
  отдельный кэш; `navigateFallback` для `/archive/<N>/*` → архивный `index.html`.
- Можно отложить в конец этапа (1.6 после 1.5), если владелец согласен, что первое время архив
  только онлайн.

### 1.7 Совместимость архива с новым кодом (гейт)
- Каждый выкат: архивная сборка + `smoke` по ней (ростеры-образцы, страницы фракций, трекер) +
  структурная проверка снимка (схема данных из `data.types.js`).
- Изменили форму данных — поднимаем версию схемы и пишем миграцию снимка в репозитории архива
  (или снимаем версию с архива — решение в момент изменения).
- Что не делаем: `sync`, `parity` и прочие гейты против appdata по архиву не гоняем — снимок
  заморожен и уже проходил их в своём релизе.

### 1.8 Первая архивная версия
- Сейчас на сайте 995. Предыдущая — 981 (бамп `f40ee336`, 2026-10-16). Её снимок брать из коммита
  перед бампом и проверить совместимость с текущим кодом **первым же шагом (разведка)** — до
  остальной работы: это главный неизвестный риск этапа.
- Если 981 несовместима дорого — архив начинается с 995, когда выйдет следующая версия GW.

### 1.9 Готово, когда
- Обычная сборка не изменилась для игрока; все гейты, `sync`, `npm test`, `smoke`, `perf` зелёные.
- `/archive/981/` работает целиком: правила, фракции, юниты, конструктор, печать, трекер; баннер
  на каждой странице; ростер помнит версию.
- Выкат собирает архив сам, гейт совместимости в нём.
- Документация: `src/data/CLAUDE.md` (виды файлов, алиас), `DEPLOY.md` (архив), скил `appdata-update`
  (заморозка), этот журнал.
