# Избранное и коллекция моделей — в аккаунт

Отчёт `d2c24c0c` (2026-09-21, игрок Grey Knights, `/ru/roster/new`): «Избранные фракции и
отметки о наличии моделек не привязаны к аккаунту, и не мигрируют с устройства на устройство. Было
бы круто синхронизировать всякую инфу пользака». Тот же игрок в этот вечер прислал ещё два отчёта
(Mandulian Reliquary — починено в 2.6.6; перестановка юнитов — свой журнал).

## Что сейчас

- Избранное (`useFavorites.js`, ключ `wh11ed-favorites`) и коллекция «что у меня есть»
  (`useCollection.js`, ключ `wh11ed-collection`) — синглтоны на localStorage, без облака.
- В облаке живут только законченные партии (`useCloudSync.js`) и сохранённые ростеры
  (`useRosterSync.js`). Правила ростерного синка — хороший образец и здесь, но не все: ростеры
  большие и уезжают по клику «Сохранить», отметки маленькие и ставятся мимоходом.
- Бэк: маршруты `games`, `rosters`, `party`, `broadcast`, `me`. Таблицы под пользовательские
  настройки нет.

## Что синхронизируем (решено 2026-09-22)

Ровно две вещи: **закреплённые фракции + избранные юниты** и **коллекция моделек**.

Опции трекера (`src/data/trackerOptions.js`, «что отслеживать») в этот список **не входят, и это
не недоделка**: они принадлежат партии, а не телефону — пишутся в `game.settings`, уезжают в
облако внутри самой партии и расходятся по устройствам в синхронизированной игре, а новая партия
наследует выбор прошлой через `defaultTrackSettings`. Два ряда помечены `local` намеренно. Вторая
группа, которую тоже не берём, — читательские переключатели устройства: остаток очков в
конструкторе (решение 2026-09-21), фильтры каталога и миссий, Legends в списке, «стратагемы по
фазам», раскрытые блоки. Это состояние экрана, а не пользователя.

## Решения по спорным местам

**Томбстоуны, а не объединение множеств.** Снятая отметка — это запись со временем снятия, а не
исчезнувший ключ; слияние идёт поэлементно, побеждает более позднее. Простое объединение ничего не
теряет, но снять отметку глобально при нём невозможно, а владелец хочет, чтобы снятие работало
сразу правильно. Цена — около 15 байт на запись. Томбстоуны живут **90 дней**, дальше подчищаются:
документ иначе только растёт. Известный размен — устройство, пролежавшее офлайн дольше трёх
месяцев, воскресит снятую на нём отметку.

**Строки по фракциям, но один запрос за визит.** Хранение построчно (плюс отдельная строка под
глобальный список закреплённых фракций) взято не ради трафика, а ради записи: клик по звёздочке
пишет одну строку, а не весь документ. А вот тянуть лениво по фракциям — нет: дефицит у нас в
запросах (потолок шлюза 1800 rpm), а не в байтах — документ типичного игрока 1–3 КБ, тяжёлого с
500 отметками ~35 КБ. Ленивая подгрузка превратила бы один GET в пять-шесть (каталог показывает
ещё и союзников) и всё равно не спасла бы слияние при входе, которому нужны все фракции сразу.
Вместо этого — один GET с `ETag`, как у трансляции: не менялось ничего — `304` и ноль трафика.

**Слияние при входе, а не замена.** Иначе вход на втором устройстве стирает то, что там отмечено
до логина.

**Уборку делает только клиент с достаточно свежими данными.** «Юнита нет в игре» и «юнита нет в
данных, которые лежат у меня» — разные вещи: установленный PWA неделями живёт офлайн на старой
версии данных, и, честно исполнив «нет юнита — удаляем из облака», он потёр бы отметки для
юнитов, которых просто не знает, — сразу у всех устройств. Поэтому облачный документ помнит, на
какой версии appdata по нему последний раз проходила уборка, и клиент с данными старше этой
отметки только сливает, но не чистит.

**Карта переименований применяется на фронте.** Бэк про датащиты не знает и знать не должен — он
хранит непрозрачные блобы, это его принцип. Следствие, с которым мирились сознательно: переезд id
и уборка случаются при следующем открытии приложения игроком, а не в момент релиза.

**Смена фракции датащитом** — отметка просто удаляется, переезд между вёдрами не городим: случай
исчезающе редкий, а код под него живёт вечно.

## Идентификаторы: что уже есть и чего не хватает

Заводить новые идентификаторы не нужно — они есть. `id` датащита (`brother-captain`) load-bearing:
на нём URL и `RouterLink`, и по конвенции он не меняется даже после переименования юнита в GW.
`src/data/sourceIds.json` — генерируемый мост к UUID из appdata, датащиты покрыты 1:1, и существует
он ровно затем, чтобы бамп читался как `⟲ renamed`, а не «пропал + появился».

Не хватает **гейта**: конвенция «id не меняется» держится на дисциплине, и ничто не падает, если
id тихо уехал. Раз теперь на этих id висят облачные отметки, нужен снимок известных id, падающий
при пропаже без явной записи в карте переименований (правило «гейты должны кусаться»). Исчез без
записи — значит юнит удалён из игры, и отметка удаляется из облака; сменил id — в облаке меняется
id. Ни дублей, ни мусора.

Pack-Legends получают детерминированные ключи в том же формате, что орочьи (орки единственные
приходят с Legends из appdata). Оговорка: пока GW не завезёт остальные Legends в appdata, свой
ключ не с чем сверять — работать он начнёт в паре с картой переименований.

## Порядок работ

1. Сначала выкатить 2.6.6 — новая фича не должна лечь поверх невыкаченного.
2. Гейт на стабильность id + карта переименований.
3. Бэк: таблица, репозиторий, `GET`/`PUT`, потолок размера, `ETag`. Схема YDB меняется — порядок
   выката в `wh11ed-api/README.md`, прод-шаги только по явному «да».
4. Фронт: слияние, дебаунс отправки, уборка по версии данных. `useFavorites`/`useCollection` умеют
   только тоглить по одному — им нужен приём целого состояния.
