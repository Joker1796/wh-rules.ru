# Переезд бэкенда из Яндекса: новый бэк с нуля

## Решение владельца (2026-10-11)

Не ждём Яндекс. Поднимаем бэкенд заново на пустой базе, старый закрываем. Основание: партии,
ростеры и отметки лежат у игроков на устройствах и зальются заново. Теряем очередь баг-репортов,
идущие совместные партии, трансляции и счёт аккаунтов.

## Что известно о сбое (на 11.10, днём)

- Сроков Яндекс не называет. ru-central1-b (Сасово) недоступна с 08.10, ru-central1-a (Владимир) — с
  04:00 11.10; 09.10 пострадал ДЦ в Калуге. Платформа в аварийном режиме, квоты ручные.
- По Telegram Яндекса (пересказ SecurityLab): оставшуюся конфигурацию считают неустойчивой,
  клиентам советуют альтернативные DR-планы, не только переключение зон.
- Оценки ремонта ДЦ от экспертов: от 1–2 месяцев до года.
- Наше: API и YDB не отвечают («Table metadata loading»), `yc` по функциям — таймаут. Сайт жив.

## Риск для статики (бакет + CDN)

Проверено 11.10 ~12:40 МСК: CDN отдаёт 200 с `cache-status: MISS`, т. е. сам ходит в бакет;
S3-API читает (`storage.yandexcloud.net` 200 за 0,5 с).

- **CDN — риск низкий** по самим краевым узлам, но он не самостоятельный: управление и источник
  (бакет) — в Яндексе. `index.html` и `sw.js` с `no-cache`, значит без бакета новые посетители
  получат ошибку почти сразу, а не через TTL.
- **Object Storage — риск средний.** Он региональный (копии в зонах региона), а из зон a/b/d/e две
  уже лежат; 08–09.10 были задержки записи, 11.10 — «возможны проблемы с записью». Чтение пока
  держится. Хуже всего — потеря записи: не сможем выкатить фронт.
- **DNS — главный незамеченный риск.** Зона `wh-rules.ru` обслуживается `ns1/ns2.yandexcloud.net`.
  Ляжет Cloud DNS — не откроется ни сайт, ни новый бэк, и переключить записи будет нельзя.
  Регистратор — REG.RU (оплачен до 2027-07-17), NS у него меняются без Яндекса.
- **Установленная PWA** переживёт всё перечисленное: работает офлайн после прогрева.

Вывод: перенести DNS из Яндекса сейчас, пока Cloud DNS отвечает и записи можно скопировать;
держать копию сборки фронта у второго провайдера, чтобы переключение было одной DNS-записью.

## Где поднимать бэк

Ограничения:
- **Сервер в России.** 152-ФЗ: персональные данные граждан РФ (почта, имя из OAuth) собираются и
  хранятся в РФ (ч. 5 ст. 18, с 01.07.2025 ужесточено). Плюс зарубежные хостинги из РФ режутся
  РКН нестабильно. Точную юридическую позицию по OAuth не нашёл — при сомнении к юристу.
- **Другая компания и другой город, чем Яндекс** (Владимир, Сасово, Калуга). Бэкап — у третьей
  стороны, не там же, где сервер.

### VPS против serverless

Сейчас платим за каждый вызов функции и YDB. Совместная партия шлёт ~4 запроса в минуту с
устройства, т. е. ~700 за трёхчасовую игру на устройство; при росте это растёт линейно. Один VPS
с Node (Hono) держит тысячи таких запросов в секунду за фиксированную цену. Реальных цифр
нагрузки и счёта сейчас нет — биллинг Яндекса недоступен.

**Рекомендация — VPS.** Фиксированная цена, никакого привязанного к облаку слоя, переезд к
другому провайдеру = скопировать Docker и дамп.

**Предложение:** бэк — Timeweb Cloud VPS (СПб); бэкап базы и запасная копия фронта — Selectel S3
(Москва). Две компании, два города, ни одной площадки Яндекса. Порядок ~1 500 ₽/мес за всё.

## Что менять в коде

- `wh11ed-api`: слой `src/db/` (~1 600 строк, самый большой — `parties.repo.ts` 505) переписать с
  YDB на **PostgreSQL** в Docker на том же VPS. Альтернатива — SQLite + Litestream (непрерывная
  копия в S3), проще, но привязывает к одной машине. Postgres выбран за то, что потом переносится
  в управляемый без переписывания.
- Запуск: `src/server.ts` + `@hono/node-server` уже есть (стенд), адаптер `yc-apigw.ts` уходит.
  Перед ним — Caddy (TLS сам).
- Секреты из Lockbox → `.env` на сервере. Почта баг-репортов через Postbox (Яндекс) → другой SMTP.
- OAuth: новый redirect URI у Яндекса и Google; если имя `api.wh-rules.ru` сохраняем — только
  смена адреса, фронт не пересобирать.
- Бэкап: `pg_dump` по cron ежедневно → S3 второго провайдера, восстановление один раз проверить.
- **Обязательно проверить на стенде до выката:** игрок с локальными ростерами/партиями и пустым
  сервером — данные заливаются, ничего не удаляется (томбстоуны в `useRosterSync`, новый id
  пользователя после входа). Иначе «зальются заново» — неправда.
