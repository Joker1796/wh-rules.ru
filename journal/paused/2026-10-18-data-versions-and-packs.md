# Версии данных и свои паки (самоделки)

> **Статус:** приостановлен
> **Репозитории:** wh11ed (позже wh11ed-api — хостинг паков)
> **Начато:** 2026-10-18
> **Связано:** [Ростер по ценам прошлой версии](2026-10-01-roster-frozen-prices.md)
> **Ждём:** владельца — «на будущее»; ответы на три вопроса внизу и порядок ступеней

## Откуда задача

Владелец, 2026-10-18:
- турнир утвердил правила по одной версии данных, а прямо перед ним вышло обновление. Сейчас
  показывается только последняя версия, предыдущую посмотреть нельзя;
- свои датащиты, правила, улучшения для нарративных кампаний. Не в основном бандле, скачиваются
  по запросу; возможно, отдельный сервис, где заполнять кастомных юнитов.

## Исходное состояние (на 995)

- Правила, датащиты и очки лежат в бандле. Версия — одно число `APP_DATA_VERSION`
  (`src/data/appDataVersion.js`) и `mfmVersion` (`src/data/mfmFactions.js`).
- Каждая прошлая версия целиком есть в git: коммиты `data(N)`. Старый RU тоже там, переводить
  заново не нужно.
- MFM всех фракций занимает ~356 КБ исходников (`src/data/mfm/`). Весь `src/data` — 21 МБ.
- `deepOverlay.js` накладывает RU на EN, но умеет только **менять** записи: не добавляет и не
  убирает.
- Схема ростера v12 (`rosterCore.js`). Экспорт уже пишет `{ app, data }` версии.

## Главная идея

Одна сущность — **пак данных**: слой поверх текущих данных. Догружается лениво, не входит в
основной бандл и всегда виден на экране. Им станут и «правила по 981», и самоделки. Нужно
обобщить оверлей до трёх операций: добавить, изменить, убрать.

## Часть 1. Версия данных — три ступени

Турниры обычно фиксируют версию MFM и дату эрраты или датаслейта («обновления за N дней до
турнира не применяются»). Полностью другие правила нужны редко.

**Ступень 0. Архивная копия на поддомене** (около дня работы).
- Прошлый релиз из git-тега выкладывается на `v981.wh-rules.ru`: без SW и без облака.
- Отдельный origin, значит отдельный localStorage. Путь `/v/981/` на том же домене опасен:
  старая сборка не знает схему ростера v12 и может её испортить.
- Ростер переносится текстом через экспорт и импорт GW.
- Хранить только предыдущую версию.
- Минусы: старый UI со старыми багами, нет офлайна.
- DNS и CDN для поддомена владелец настраивает руками: классификатор не пускает менять CDN.

**Ступень 1. Очки по версии MFM в ростере.** Главный турнирный случай.
- Прошлые MFM собираются ленивыми чанками из git-истории `src/data/mfm/`.
- В ростере поле «Очки по MFM: 1.6 / 1.5». Экспорт и печать пишут выбор.
- Юнита нет в старом MFM — показывать «нет цены в 1.5», а не 0.
- Трекер берёт снимок ростера, его не задевает.
- Вопрос из связанного журнала: одни цены без правил дадут список, который по очкам старый,
  а по составу и валидации текущий. Это надо подписать честно.

**Ступень 2. Откат правил к предыдущей версии.** Только если 0+1 не хватит.
- При каждом бампе данных sync сохраняет **обратную дельту**: изменённые датащиты, стратагемы и
  улучшения со старым EN/RU. У appdata уже есть `changes.json`.
- Дельта — пак, обычно десятки КБ.
- UI: переключатель «Версия правил: 995 / 981»; на затронутых страницах плашка «показано по 981
  · изменено в 995»; бонус — «что изменилось» на странице юнита.
- Выход кодекса — замена фракции целиком, а не дельта. В этом случае отправляем на ступень 0.

**Не делать:** все версии целиком в бандле. Противоречит лёгкой вкладке и кратно раздувает
precache установленного приложения.

## Часть 2. Самоделки

**Формат пака.**
- JSON в форме наших данных: датащит, детачмент, улучшения, стратагемы, правило армии.
- EN обязателен, RU по желанию.
- id в пространстве `hb:<pack>:<id>`.
- Поля `author`, `version`, `basedOn: <data version>`.
- zod-схема общая для фронта и API; пак проверяется при загрузке.
- **Безопасность:** текст чужой. Рендер только через наш markdown без HTML. Перед стартом
  проверить, что рендерер экранирует ввод: раньше данные были только свои.

**Загрузка.**
- В основном бандле только крючок «есть ли паки». Загрузчик, слияние с индексами и редактор —
  ленивый чанк.
- Установка файлом, ссылкой или кодом. Хранение в IndexedDB, облачная синхронизация потом.
- Значок «Самоделка» с именем пака везде: поиск, юнит, ростер, печать.
- Ростер помнит `pack@version`. Без пака показывать «нужен пак X».
- Флаг ростера «турнирный» скрывает паки.

**Редактор.**
- Этап 1: ленивый раздел `/workshop`.
  - Форма юнита: профиль, оружие, способности, ключевые слова, очки.
  - Живое превью официальными компонентами датащита.
  - Экспорт в файл. Бэкенд не нужен.
- Этап 2: хостинг в `wh11ed-api` (Postgres).
  - Таблица `packs`: владелец, версии, лимит размера.
  - Доступ только по ссылке, без каталога.
  - Жалоба и удаление.
- Отдельный сервис — только для совместного редактирования кампании или каталога.

**Кампании (Crusade-подобное):** опыт, награды, реквизиции — отдельная фича трекера со своим
форматом. Обсуждать после паков.

**Риск:** хостинг позволит залить платный текст GW. Меры: только ссылки, лимит размера, удаление
по жалобе. Решение за владельцем.

## Предложенный порядок

1. Ступень 1: очки по MFM.
2. Ступень 0: архив на поддомене.
3. Формат пака и обобщённый оверлей; загрузка из файла; значок.
4. `/workshop` с превью.
5. По спросу: ступень 2 и хостинг паков.
