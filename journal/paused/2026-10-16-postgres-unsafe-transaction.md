# `UNSAFE_TRANSACTION` под нагрузкой записи

Нагрузочный тест синхронизации партий на стенде (2026-10-16, контейнер API ограничен одним ядром,
Apple M5): при ~1240 записях в секунду 11 запросов из ~51 000 ответили 500 —
`Error: UNSAFE_TRANSACTION: Only use sql.begin, sql.reserved or max: 1` из драйвера `postgres`
(^3.4.5), `connection.js` `CommandComplete`. Наш `transaction()` (`src/db/driver.ts`) вызывает
`db().begin('isolation level serializable', fn)` — по коду верно; исходники драйвера мне читать
запрещено (node_modules), так что причина не установлена. Гипотезы: гонка драйвера при `begin` с
опциями под высокой конкуренцией пула, или повтор после 40001.

Воспроизвести: скрипт нагрузки (создать N партий через `/dev/jwt` + `POST /party`, гонять
`POST /party/:id/sync` с записью `side0`, разные `X-Forwarded-For`) — пересобрать по описанию,
scratchpad сессии не сохранился.

## Замеры той же сессии (для справки)

Одно ядро стенда: пустой опрос ~2800/с при 77% CPU (потолок ~3600), запись ~1240/с при 100%.
Прод: Selectel, Xeon Gold 6240R 2.4 ГГц, 2 vCPU, 2 ГБ; Node занимает одно ядро. Оценка прода
~1500 пустых опросов или ~500 записей в секунду → ~1500 телефонов одновременно с запасом ×2 при
шаге 2 с. По этим цифрам шаг опроса снижен до 2 с (лобби 4 с), кэш API 2 с, лимит на адрес 2400/мин.

## 22.10: что известно о драйвере (разбор issue при обновлении зависимостей)

Это пересказ разбора помощником; перед правкой перепроверить по самим issue.

- Ошибка не исправлена ни в postgres 3.4.9, ни в master: issue #823, #1189, #1210, #1264 открыты, исправление в PR #1207 тоже открыто.
- **Механизм.** `sql.begin()` отправляет `BEGIN` в очередь занятого соединения. Под нагрузкой цепочка в `execute()` прерывается, и соединение не помечается занятым.
- **Опасность.** По воспроизведению в #823 после такой ошибки сокет остаётся внутри транзакции. Последующие записи на нём молча откатываются или коммитятся в чужой транзакции. **Повтор на `UNSAFE_TRANSACTION` не добавлять.** Наш `transaction()` повторяет только 40001 и 40P01, и это верно.
- **Что рассмотреть:**
  - транзакции через `sql.reserve()` с ручным `BEGIN … COMMIT`;
  - считать соединение после ошибки негодным;
  - `idle_in_transaction_session_timeout` в Postgres;
  - следить за `idle in transaction` в `pg_stat_activity`.

## 22.10: замер на стенде (Mac, API на хосте, Postgres стенда)

- 250–300 партий по ~600–700 записей в секунду, 25 секунд на круг.
- `UNSAFE_TRANSACTION` — примерно 1 на 15–45 тыс. записей. Частота одинаковая на драйвере 3.4.5 и 3.4.9 (5 кругов поочерёдно).
