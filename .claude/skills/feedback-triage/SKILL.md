# Разбор жалоб игроков

## 1. Прочитать очередь

Очередь живёт в Postgres на сервере Selectel (с 2026-10-11; YDB больше нет). Скрипты лежат в
образе API — запускать их в контейнере по ssh, локально `DATABASE_URL` к проду не нужен:

```bash
FB() { ssh -i ~/.ssh/wh_rules_vps wh@31.129.57.24 \
  "cd /opt/wh-rules && docker compose -f docker-compose.prod.yml exec -T api node --import tsx scripts/$*"; }
FB feedback-list.ts                  # дайджест, свежие сверху
FB feedback-list.ts <id-префикс>     # один отчёт целиком: контекст, ошибки, вложение
FB users-count.ts                    # сколько аккаунтов всего и по месяцам
```

Чтение с прода владелец разрешил (2026-10-12). В zsh не печатать разделитель `=====` голым
`echo` — это раскрытие `=cmd`, цикл падает.

В отчёте есть версия приложения, маршрут, последние JS-ошибки и — если игрок отметил галочку —
партия или ростер. Контакта у отправителя нет: ответ уходит не письмом, а правкой и записью в
чейнджлоге.

## 2. Проверить, а не поверить

**Каждая жалоба проверяется по первоисточнику до вердикта.** История показала оба направления
ошибки: и «это не баг» на настоящем баге, и «appdata врёт» там, где врали мы.

- Правила и датащиты — `wh40k-appdata` (ветка `master`), очки — MFM.
- Считать арифметику руками, а не сверять формулировки.
- Не нашёл подтверждения — так и сказать («не воспроизводится, нужны детали»), а не додумывать.
- Игрок может помнить 10-ю редакцию; это тоже вердикт, но только после проверки.

## 2а. Разобрать до корня — до молекул (решение владельца 2026-10-07)

Починить случай из жалобы — это половина работы. Ошибка игрока почти всегда — один экземпляр
**класса**, и остальные экземпляры игроки ещё не нашли. Каждый баг (из репорта или найденный нами)
проходит все шаги, и в отчёте владельцу видно, что каждый пройден:

1. **Механизм.** Почему код/данные дали этот результат — конкретная строка, функция, поле, а не
   «что-то с заменами». Воспроизвести на реальных данных (тест или probe), до правки.
2. **Корень.** Почему механизм так устроен: неверное правило чтения, точное сравнение имён,
   поле на группу там, где нужно на вариант, урок, записанный только в один скрипт. Чинить корень,
   а не подкладывать исключение под один случай — если исключение всё же нужно, назвать почему.
3. **Класс — весь, а не узкий шаблон.** Найти все места того же вида во ВСЕХ данных и коде:
   не одной регуляркой под формулировку из жалобы, а широким сбором (например, все инструкции с
   «or» в первой строке) и разбором каждой группы руками. 2026-10-07: «replaced with X, or
   equipped with» нашло один случай, а владелец справедливо спросил про остальные «или» — полный
   сбор дал 17 формулировок, каждую надо было классифицировать с самого начала.
4. **Соседние пути.** Где ещё тот же вопрос решается тем же способом (список ростеров и трекер
   искали детачмент одинаково — урок 78). Грепать код на то же сравнение/поле.
5. **Почему не поймали раньше.** Какой гейт должен был сработать и почему молчал; если гейта нет —
   завести и **доказать, что он красный на старом коде**.
   Если баг сидел в коде (`wh11ed/src/core`, `wh11ed-api/src`), прогнать по этому файлу
   `npm run mutate -- <файл>`: выжившие мутанты — соседние места, где тесты так же ничего не
   держат (с 2026-10-27; что читать в выводе — `wh11ed/src/core/CLAUDE.md`).
6. **Записать.** Урок в `wh11ed/APPDATA-SYNC-LESSONS.md` (или scoped CLAUDE.md), если класс может
   вернуться с данными; отчёт генератора печатает каждый случай по имени.

В ответе владельцу — механизм, корень, размер класса (сколько найдено и что с каждым), гейт.

## 2б. Сначала разбор и решение, правки — по команде (владелец, 2026-10-16)

Порядок работы с отчётами:

1. **Разбор** каждого отчёта по §2–2а: механизм, корень, весь класс, почему гейт молчал. Ничего
   не править — только читать, считать, воспроизводить (независимые отчёты можно разбирать
   параллельно, помощникам — только исследование).
2. **Решение для класса** — владельцу одним ответом по каждому отчёту: вердикт (баг / не баг /
   отдельная задача), размер класса, предлагаемая правка, гейт, а для «не бага» — текст ответа.
3. **Правки — только по команде владельца.** «Изучи и предложи» ≠ «делай»: ветки, коммиты, данные
   и слияние в релиз ждут его слова.

## 3. Развести на три кучи

- **Наш баг** → правка + гейт, который поймал бы это раньше. Если гейта нет — завести: каждый
  существующий гейт появился потому, что баг первым нашёл игрок.
- **Не баг** → записать почему, чтобы второй раз не разбирать заново, и **ответить в чейнджлоге**
  (владелец, 2026-10-16): у отправителя нет контакта, а вопрос, скорее всего, есть и у других.
  Пункт в записи ближайшего релиза — голосом владельца (скил `changelog-entry`): что спросили и
  как на самом деле по правилам, с названиями юнитов/опций как в датащите. Пример: «Sanctifiers
  могут взять либо мельту, либо Holy fire, но не оба. Плазма есть только у одного Missionary, и
  обе опции — для неё».
- **Отдельная задача** → журнал в `journal/paused/` хаба с описанием, а не строчка в конце
  чужого документа: там она потеряется.

## 4. Закрыть

Команда владельца → правки → скил `data-gates` → запись в `changelog.js` (и исправления, и ответы
на «не баг») → релиз (скил `release-frontend`).
Если из разбора родился переиспользуемый приём — в `wh11ed/APPDATA-SYNC-LESSONS.md`.

**Разобранные отчёты удалять из базы** (решение владельца 2026-09-19) — таблица `feedback` это
входящие, а не архив; вердикт к этому моменту уже записан в чейнджлог, журнал или ответ
пользователю. Так же через контейнер:

```bash
FB feedback-delete.ts <id-префикс> [<id-префикс> …]   # префикса из дайджеста (8 символов) достаточно
```

Скрипт отказывается, если префикс не найден или неоднозначен, — ничего не удаляя. Смоук-записи,
оставленные при проверке самой формы, удалять тем же способом.
